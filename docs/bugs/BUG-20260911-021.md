# 群 Agent 已加入 OpenIM，但管理页与提及候选缺失

## 现象

群 `67aa59ad-e315-4f2f-b3f6-63f3216a863f`（一版一发群）在成员编辑界面选中了自己的 Agent，但保存后管理页和 `@` 候选没有该 Agent。

## 复现 Case

Given 群主在云端群成员编辑器中选择自己拥有的 Agent
When 群主保存成员并回到群消息输入框键入 `@`
Then 后台房间、OpenIM 群成员、管理页选中状态和 `@` 候选应一致包含该 Agent

实际结果：OpenIM 已加入 Agent，但桌面 UI 使用的房间业务快照没有一致呈现该成员。

## 现场证据

- 本机 OpenIM 数据库的群标识为 `grp_67aa59ade3154f2fb3f663f3216a863f`。
- 当前 OpenIM 成员为 `xuxin`、`kexi` 和 Agent `架构师`（`agt_0a630169cf7947268ba916542ee8a65e`），成员数为 3。
- 2026-09-11 17:19:07 的 OpenIM 通知确认 `架构师` 被邀请入群；同一批成员替换操作将 `程序员`（`agt_b12d303e119043dbaa99ea7174cb634a`）移出群。
- 本地 Agent 映射确认 `架构师` 的云端 UUID 为 `0a630169-cf79-4726-8ba9-16542ee8a65e`，所有者为当前用户。
- 新建群 `2e09bb6e-6cf0-4448-af00-cad0b1e24618` 再次复现：桌面提示“群已保存，但以下 Agent 尚未同步：架构师。请重试。”，但对应 OpenIM 群 `grp_2e09bb6e6cf04448af00cad0b1e24618` 已有 `xuxin`、`kexi` 和 `架构师` 三名成员。
- 该二次复现发生在新桌面同步校验已经生效、目标远端 API 尚未部署房间查询修复的混合版本阶段；提示来自一致性保护，不代表 OpenIM 邀请失败。

## 代码证据

- 群成员保存使用 `PUT /v1/rooms/:id/members`，语义是整体替换而不是增量邀请。
- 云端工作区把后台 `room.agents` 映射为 `room.agentIds`；输入框只用 `state.agents` 与 `room.agentIds` 的交集生成 `@` 候选。
- OpenIM 的 `local_group_members` 没有参与管理页选中状态或 `@` 候选生成，因此后台快照、目录映射或同步状态任一缺失时，UI 会隐藏实际已经在 OpenIM 群内的 Agent。

## 根因

`GET /v1/rooms` 并行查询的实际顺序是“好友成员、工作区绑定、Agent 成员”，但结果被错误解构为“好友成员、Agent 成员、工作区绑定”。因此 `room.agents` 得到的是 workspace binding 行或空数组，真实 `room_agents` 没有进入桌面快照。OpenIM Outbox 独立消费正确的成员变更，所以形成了“OpenIM 已经有 Agent、管理页与 `@` 候选却没有”的双源不一致。

此外，其他群成员的全局可用 Agent 目录不会包含群内的私有 Agent。即使修正服务端解构，桌面若仍只用全局目录建立索引，好友端也无法把房间 Agent ID 解析成提及候选。

## 修复

- 修正房间并行查询结果的解构顺序，让 `agents` 与 `workspaceBinding` 回到正确字段。
- 房间 Agent DTO 返回不含指令和密钥的安全摘要；桌面把房间独有 Agent 补入索引，已有完整 Agent 定义保持优先。
- 保存群成员后核对所有非待审批 Agent 是否出现在同步结果中；不一致时保留弹窗并显示具体 Agent。
- 管理页明确说明保存是整体替换，并实时列出将加入和将移出的 Agent。
